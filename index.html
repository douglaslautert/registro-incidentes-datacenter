Problema a resolver

O datacenter opera sem sistema centralizado de registro de falhas. Quando um servidor cai, o horário real do início da falha se perde — o técnico só registra quando chega ao equipamento. Peças trocadas ficam em planilhas locais sem vínculo com o equipamento ou histórico. Não há como calcular MTTR, identificar recorrências nem justificar orçamento de reposição com dados.

Resultado: ausência de rastreabilidade, dificuldade em acionar garantias com fornecedores (sem número de chamado) e impossibilidade de gerar relatórios gerenciais sem trabalho manual.

Etapa 4 · Definição da Arquitetura e Componentes

Arquitetura

Estilo arquitetural: monolítico modular

Dois monolitos bem definidos — GLPI e Zabbix — integrados por um único ponto de comunicação: o webhook HTTPS. Esta é a arquitetura correta para o contexto, não uma limitação.

Estilo consideradoDecisãoJustificativa
Monolítico modular✅ EscolhidoEquipe pequena, domínio estável, escala previsível, zero custo de licença, APIs REST maduras
MicrosserviçosDescartadoOverhead operacional desproporcional. A equipe não tem capacidade de operar Kubernetes, service mesh e observabilidade distribuída sem ganho real no volume desta instalação.
Orientado a eventos (Kafka)DescartadoWebhook síncrono já atende < 5 s. Broker adicionaria single point of failure sem benefício.
SaaS (Freshservice)DescartadoDados de infra fora da universidade — viola política de segurança. Custo por técnico incompatível com orçamento público.
Sistema próprio (Opção F)DescartadoGLPI atende 72% nativamente. Desenvolver do zero: prazo + manutenção + dependência de quem escreveu = risco de legado imediato.

Decisões de arquitetura (ADRs)

ADR-01
GLPI como sistema de registro
Decisão: usar GLPI; campos extras via Plugin Fields.
Trade-off aceito: UI datada e configuração inicial alta — aceitos em troca de zero licença, on-premises, API REST madura e 72% dos campos nativos.
Descartado: sistema próprio — prazo incompatível e manutenção dependente de quem escreveu.
ADR-02
Zabbix abre chamado por webhook síncrono
Decisão: Media Type JS no Zabbix faz POST na API do GLPI em < 5 s.
Trade-off aceito: dependência temporal entre Zabbix e GLPI — mitigada por retry (3 × 60 s) e health check.
Descartados: abertura manual (perde timestamp) e broker de mensagens (overhead sem ganho).
ADR-03
Um banco por ferramenta
Decisão: Zabbix no PostgreSQL, GLPI no MariaDB. Integração só pela API.
Trade-off aceito: dois bancos para backup e monitorar — aceito por atualizações independentes e rollback isolado.
Descartado: banco compartilhado — acopla versões; atualização de schema de um quebra o outro.
ADR-04
Anexos em volume de disco (plano B: MinIO)
Decisão: volume local 500 GB + backup diário rsync.
Trade-off aceito: menos elástico que object storage — aceito para MVP.
Reavaliar: uso > 400 GB → migrar para MinIO (S3-compatible, suportado pelo GLPI 10+).
ADR-05
NetBox na Fase 2, IA na Fase 3
Decisão: NetBox aguarda cadastro completo do inventário; IA aguarda decisão sobre LLM local vs. externo.
Trade-off aceito: MVP sem localização automática e sem causa raiz por IA — o valor central é entregue mesmo assim.
Condição da IA: Ollama local por padrão, ou aval formal documentado para provedor externo.
ADR-06
On-premises em duas VMs no Proxmox
Decisão: VM-ZABBIX + VM-GLPI no cluster Proxmox existente.
Trade-off aceito: a equipe opera a infra — aceito porque já opera o datacenter; duas VMs a mais é marginal.
Descartado: SaaS — dados fora da universidade viola política de segurança; custo por técnico incompatível com orçamento público.

Guia de Implementação

Implementação passo a passo

Antes de qualquer passo: tirar snapshot da VM-GLPI no Proxmox. Qualquer erro de configuração pode corromper dados existentes.

Ordem de execução

1
Snapshot da VM-GLPI no Proxmox
Proxmox UI → VM-GLPI → Snapshots → Take Snapshot. Nomeie com a data: pre-zabbix-20261017.
2
Criar VM-ZABBIX no Proxmox
qm create 201 --name vm-zabbix --memory 8192 --cores 4 --net0 virtio,bridge=vmbr0
Adicionar disco 100 GB SSD + ISO Ubuntu 22.04 → iniciar para instalação.
3
Configurar inventário e variáveis Ansible
Editar ansible/inventory/hosts.ini com IPs reais. Criptografar senhas: ansible-vault encrypt_string 'senha' --name 'var'.
4
Rodar playbook de instalação do Zabbix
ansible-playbook site.yml --tags zabbix,firewall,backup --ask-vault-pass
Aguardar conclusão (~15 min). Verificar Zabbix Frontend em HTTPS.
5
Criar usuário de serviço no GLPI
Rodar scripts/glpi_setup_service_user.sh. Copiar o user_token retornado para o group_vars/all.yml (via vault).
6
Configurar Media Type GLPI no Zabbix
Rodar scripts/setup_zabbix_mediatype.py com as variáveis de ambiente. Verificar em Zabbix → Administration → Media Types → GLPI Webhook.
7
Criar regras de categorização no GLPI
Rodar scripts/glpi_setup_rules.py. 9 regras criadas: Hardware/Fonte, Rede/Interface, Performance/CPU, Ambiente/Temperatura, etc.
8
Configurar Plugin Fields no GLPI
GLPI UI → Setup → Plugins → Fields → criar campos: "Chamado do fornecedor", "Executor", "Origem da peça" vinculados ao tipo Chamado.
9
Validar webhook com chamado de teste
Zabbix → Configuration → Actions → criar action de teste com trigger falsa. Confirmar chamado criado no GLPI em < 5s. Ver log: grep -i webhook /var/log/zabbix/zabbix_server.log | tail -20.
10
Configurar monitor da VM-GLPI no Zabbix
Rodar scripts/zabbix_setup_glpi_monitor.py. Web scenario criado: verifica API a cada 60s; trigger se GLPI não responder em 30s.

Script do webhook

O webhook é um Media Type JavaScript configurado dentro do próprio Zabbix. Não precisa de servidor externo.

javascriptansible/roles/zabbix/files/glpi_webhook.js (trecho essencial)
// Mapeamento severidade Zabbix → prioridade GLPI
// Zabbix: 0=Not class 1=Info 2=Warning 3=Average 4=High 5=Disaster
// GLPI:   1=Very low 2=Low 3=Medium 4=High 5=Very high 6=Major
var SEV_MAP = {'0':1, '1':2, '2':3, '3':3, '4':5, '5':6};

if (params.event_value === '1') {
  // PROBLEM — abrir chamado
  var ticket = GLPI.request('POST', '/Ticket', {
    'input': {
      'name': '[Zabbix] ' + params.trigger_name + ' — ' + params.host_name,
      'content': 'Host: ' + params.host_name + '\nTrigger: ' + params.trigger_name +
                 '\nSeveridade: ' + params.trigger_sev +
                 '\nInício: ' + params.event_date + ' ' + params.event_time,
      'priority': SEV_MAP[params.trigger_sev] || 3,
      'type': 1, 'status': 1
    }
  });
  return JSON.stringify({ticket_id: ticket.id});
} else {
  // RECOVERY — atualizar chamado com horário de fim
  GLPI.request('PUT', '/Ticket/' + params.glpi_ticket_id, {
    'input': {
      'status': 5,
      'solution': 'Recuperação automática pelo Zabbix em ' +
                  params.event_date + ' ' + params.event_time
    }
  });
}

  become_user: postgres

- name: Habilitar serviços
  systemd: name: "{{ item }}" enabled: yes state: started
  loop: [zabbix-server, zabbix-agent2, nginx, php8.1-fpm]

Restaurar GLPI após falha grave

bash
# 1. Parar Apache
systemctl stop apache2

# 2. Restaurar banco (ajustar data do backup)
BACKUP="20261017_020001"
zcat /mnt/backup/datacenter/glpi/$BACKUP/glpi_db.sql.gz | mysql glpi

# 3. Restaurar arquivos
rsync -a --delete /mnt/backup/datacenter/glpi/$BACKUP/files/ /var/lib/glpi/files/
chown -R www-data:www-data /var/lib/glpi/

# 4. Reiniciar e verificar
systemctl start apache2
curl -sk https://glpi.intra/apirest.php | grep -c session
